# Архитектура

Документ для того, кто будет это менять. README отвечает на вопрос «как этим пользоваться»; здесь — почему устроено именно так и где границы принятых решений.

## Поток данных

```
content/ru/articles/*.mdx
        │  gray-matter — разделение frontmatter и тела
        ▼
src/content/schema.ts     Zod: нормализация даты, проверка календаря,
        │                 обязательный coverAlt при наличии cover
        ▼
src/content/index.ts      обход файлов, валидация, сортировка,
        │                 время чтения, фильтр status: draft
        ▼
src/content/mdx.tsx       remark-gfm → rehype-slug → autolink → pretty-code
        │                 белый список: Figure, Video, Callout
        ▼
src/app/**                generateStaticParams + generateMetadata
        │
        ▼
.next/standalone          готовый HTML, отдаётся node server.js
```

Всё это происходит **на сборке**. В рантайме нет ни компилятора MDX, ни Zod-валидации контента, ни обращений к файлам `content/`.

## Границы модулей

### `src/content/index.ts` — единственная точка доступа

Публичный контракт:

```ts
getAllArticles(opts?: { includeDrafts?: boolean }): Promise<Article[]>
getArticleBySlug(slug: string): Promise<Article | null>
getAllSlugs(): Promise<string[]>
getPage(slug: string): Promise<Page | null>
```

Плюс две функции для инструментов — `getAllArticlesForTooling`, `getAllPagesForTooling` — и `collectContentProblems` для валидатора. Они отдельны от публичного контракта осознанно: инструменты обязаны видеть черновики, потому что черновик с битой датой должен падать в CI до публикации, а не после.

Инвариант, который стоит защищать при любых правках: **вне этого модуля нет ни одного импорта `node:fs`**. Проверяется грубо и надёжно:

```bash
grep -rn "node:fs" src/ --include="*.ts" --include="*.tsx" | grep -v "src/content/"
```

Пока это выполняется, замена реализации на генерируемый индекс, ISR или внешний API не затрагивает ни одну страницу.

### Кэширование

Контент читается один раз на процесс в продакшене и не кэшируется в разработке. В продакшене файловая система не меняется под работающей сборкой, поэтому перечитывать её для каждой из сотен страниц — чистая трата. В разработке весь смысл в том, чтобы правка документа была видна после обновления страницы, поэтому кэш там был бы багом, а не оптимизацией.

Следствие, о котором надо помнить в тестах: `NODE_ENV` читается в момент вызова, а не при импорте. Тест, подменяющий его, обязан сбросить модули — иначе он тихо проверит поведение тестового окружения. Так и сделано в [`tests/content.test.ts`](../tests/content.test.ts).

## Разбор решений

### Почему валидация фатальна

Альтернатива — пропустить битый документ и собрать сайт без него. Это удобно ровно один раз и дорого всё остальное время: «материал просто не появился на сайте» — самый неприятный класс баг-репортов, потому что нигде ничего не сказано, и искать приходится с нуля.

Поэтому невалидный frontmatter бросает `ContentError` с именем файла и списком проблем, а `content:check` возвращает 1.

### Почему ошибки YAML тоже перехватываются

Обещание «читаемая валидация», покрывающее только семантические ошибки, ломается на первом же незакавыченном двоеточии: `js-yaml` выбрасывает исключение с сорокастрочным стеком, в котором нет имени файла. Это ровно тот опыт, от которого проект избавляет.

`readDocument()` перехватывает исключение парсера и приводит его к тому же формату, добавляя подсказку про кавычки — потому что на практике ошибка именно эта. Формулировка самого парсера («incomplete explicit mapping pair») никому не помогает.

### Почему дата — не просто строка по регулярке

Три отдельные проблемы, каждая находится не сразу:

1. **YAML типизирует незакавыченную дату сам.** `2026-02-18` — это по спецификации YAML timestamp, поэтому `gray-matter` отдаёт `Date`, а не строку.
2. **Дата со временем и смещением неоднозначна.** `2026-02-19T01:00:00+03:00` в UTC — это 18 февраля. Дата публикации, зависящая от часового пояса читателя, хуже упавшей сборки, поэтому такой вариант отвергается, а не усекается.
3. **Регулярка не знает календаря.** `^\d{4}-\d{2}-\d{2}$` пропускает `2026-02-31`, и такая дата доезжает до `lastModified` в sitemap как `Invalid Date`.

### Почему `evaluate`, а не `compile`

Документация `@mdx-js/mdx` предупреждает, что `evaluate` выполняет `eval`, и советует `compile` с записью в файл. Предупреждение относится к недоверенному вводу.

Здесь каждый документ — файл этого репозитория, попавший в него через pull request, то есть настолько же доверенный, насколько остальной код. `evaluate` избавляет от промежуточного шага сборки со своей инвалидацией кэша.

**Если контент когда-нибудь станет пользовательским, это первая строка, которую надо менять.** Именно поэтому граница названа и здесь, и в коде.

### Почему `dynamicParams = false`

Без этого неизвестный slug рендерится по запросу. Формально это удобно, фактически — полностью статический сайт незаметно становится частично динамическим, и первым признаком оказывается сервер, делающий работу, которой от него не ждали. Явный 404 честнее.

### Почему типографика написана руками

`@tailwindcss/typography` — отличный плагин и примерно двести стилей, из которых односайтовый проект на одном языке использует пятнадцать. Дальше каждый его дефолт нужно переопределять под дизайн, и объём переопределений превышает объём того, что написано напрямую. Сорок строк в `globals.css` дешевле и не оставляют второго мнения о том, как выглядит абзац.

## Инфраструктура

### Три стадии образа

- **deps** — только `package.json` и `package-lock.json`, затем `npm ci`. Слой переиспользуется на каждой сборке, где зависимости не менялись. Скопировать сюда исходники — значит инвалидировать установку на каждой правке.
- **builder** — исходники, валидация контента и медиа, `next build`.
- **runner** — `node:22-alpine`, копируются `.next/standalone`, `.next/static` и `public`. Ничего не устанавливается.

Валидация внутри `builder` дублирует шаг CI намеренно: образ — это артефакт, который уезжает в прод, и не должно быть способа собрать его из контента, который CI бы отверг.

### Почему `web` не публикует порты

В `docker-compose.yml` у сервиса `web` только `expose`, без `ports`. Единственный вход — через Caddy, поэтому на хосте не остаётся второй, незашифрованной двери, открытой по недосмотру.

### Почему адрес Caddy в переменной

`{$SITE_ADDRESS}` даёт локально `localhost` с локальным сертификатом, а на сервере — реальное имя с сертификатом Let's Encrypt. Конфиг, который тестировали локально, — это в точности конфиг, который работает в проде.

### Кэш изображений

`next/image` создаёт производные при первом запросе и пишет их в `.next/cache/images`. Каталог создаётся и передаётся пользователю `node` в Dockerfile, потому что процесс не работает под root и сам создать его не может. Том в compose нужен, чтобы каждый деплой не перекодировал все картинки заново.

## Что проверять при изменениях

- `grep` на `node:fs` вне `src/content/` — пусто.
- `npm run content:check` падает, если испортить frontmatter.
- `npm run media:check` падает, если удалить файл, на который ссылается статья.
- Черновик не появляется в выводе `npm run build`.
- CI зелёный на pull request, а не только на `main`.
