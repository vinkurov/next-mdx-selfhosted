Контентный сайт кажется простой задачей примерно до третьей статьи. Дальше
выясняется, что решения, принятые в первый день — где лежат файлы, кто проверяет
поля, что попадает в рантайм — определяют, сколько будет стоить каждое следующее
изменение.

Этот репозиторий — зафиксированный набор таких решений. Ниже разбор каждого: что
выбрано, чего это стоит и когда выбор становится неправильным.

Ключевое здесь — граница пунктира. Ни MDX-компилятора, ни TypeScript, ни Tailwind,
ни базы данных в рантайме нет. Работающий сайт — это `node server.js`, отдающий
заранее собранный HTML, и Caddy перед ним.

## Решение 1: контент вне `app/`

Соблазн — положить `.mdx` рядом с роутами и получить URL бесплатно от файлового
роутинга. Экономия примерно двести строк загрузчика.

Цена выясняется позже: **структура каталогов становится структурой URL**. Любое
изменение раскладки файлов превращается в смену адресов, то есть в редиректы,
которые надо не забыть, и потерянные внешние ссылки, о которых узнаёшь из падения
трафика.

Здесь `content/` лежит рядом с `src/`, а между ними один модуль:

```ts title="src/content/index.ts" showLineNumbers
export async function getAllArticles(opts?: {
  includeDrafts?: boolean
}): Promise<Article[]>
export async function getArticleBySlug(slug: string): Promise<Article | null>
export async function getAllSlugs(): Promise<string[]>
export async function getPage(slug: string): Promise<Page | null>
```

Наружу не просачивается ничего о файлах: ни путей, ни `fs`, ни расширений.
Утверждение проверяется грубо, но честно:

```bash
grep -rn "node:fs" src/ --include="*.ts" --include="*.tsx" | grep -v "src/content/"
```

Пусто. Значит замена реализации на генерируемый индекс, ISR или внешний источник —
правка одного файла, и ни одна страница не затронута.

## Решение 2: схема проверяется на сборке, а не в рантайме

Frontmatter пишется руками, поэтому ошибётся каждый. Вопрос только в том, где это
обнаружится.

Схемы описаны в Zod, типы выводятся из них через `z.infer` — не дублируются
руками. Две написанные декларации разъезжаются при первой правке одной из них, и
разъезжаются молча: компилятор доволен, рантайм отвергает настоящие документы.

Важна не сама проверка, а форма сообщения. Zod по умолчанию скажет
`Invalid input: expected string, received undefined` — это описание системы типов,
а не ошибки человека. Автор, забывший строку `description:`, должен прочитать
именно это:

```text
content/ru/articles/x.mdx
  description: обязательное поле отсутствует
  date: ожидается формат YYYY-MM-DD — получено "12.03.2026"
```

Название поля первым, потому что именно его ищут глазами. Полученное значение в
кавычках, потому что «ожидается YYYY-MM-DD» бесполезно рядом с тем, что человек
реально написал.

### Две ловушки, найденные при написании этого репозитория

**YAML типизирует дату сам.** Незакавыченное `2026-02-18` — это по спецификации
YAML _timestamp_, поэтому `gray-matter` отдаёт объект `Date`, а не строку.
Требовать кавычки от авторов бессмысленно: забудут через статью. Схема принимает и
то и другое — но дату **со временем** отвергает: `2026-02-19T01:00:00+03:00` в UTC
это 2026-02-18, и дата публикации, съезжающая от часового пояса читателя, хуже
упавшей сборки.[^yaml]

**Регулярка не проверяет календарь.** `^\d{4}-\d{2}-\d{2}$` пропускает
`2026-02-31`, и такая дата доезжает до сортировки и до `lastModified` в sitemap как
`Invalid Date`. Проверка, что разобранная дата возвращается теми же цифрами, ловит
это на сборке.

## Решение 3: белый список компонентов

Внутри MDX доступны ровно три компонента:

```ts title="src/content/components.ts"
export const mdxComponents = { Figure, Video, Callout }
```

Явный объект, никогда не спред. Смысл — не безопасность: контент лежит в
репозитории и проходит через pull request в любом случае. Смысл в ревью.

<Callout>
  Документ, которому доступны три известных компонента, читается в PR как текст и данные.
  Как только возможны произвольные импорты, ревью контента становится ревью кода — и
  свойство «контент это просто данные» тихо исчезает.
</Callout>

Добавить компонент — одна строка здесь и одна в README. Это трение и есть фича.

## Решение 4: только SSG, без ISR

Все страницы генерируются на сборке. `dynamicParams = false`, поэтому неизвестный
slug отдаёт 404, а не рендерится по запросу — иначе полностью статический сайт
незаметно становится частично динамическим, и первый признак этого в том, что
сервер делает работу, которой от него никто не ждал.

ISR имеет смысл, когда время сборки перестаёт устраивать — это порядка нескольких
тысяч документов. До этого он добавляет кэш, инвалидацию и класс ошибок «на
странице старая версия» в обмен ни на что.

## Решение 5: standalone-образ

`output: 'standalone'` трассирует модули, которые сервер реально достаёт, и
складывает их в `.next/standalone`. Рантайм-стадия Dockerfile **ничего не
устанавливает** — копирует готовое.

Измеренные цифры на этом репозитории — `linux/arm64`, метрика `docker images`:

| Что                                                     | Размер          |
| ------------------------------------------------------- | --------------- |
| Итоговый образ                                          | 345 МБ          |
| из них база `node:22-alpine`                            | 229 МБ          |
| слой приложения                                         | 87 МБ           |
| `@img` (libvips для `sharp`) внутри                     | 44 МБ           |
| TypeScript, ESLint, Tailwind, компилятор MDX в рантайме | нет — проверено |

Две оговорки, без которых цифра врёт. Первая: больше половины образа — это база, и ориентир «150–200 МБ» достижим на amd64, где alpine меньше. Вторая: `@shikijs` на 11 МБ в образе всё-таки остался, потому что Shiki резолвит темы и языки динамически и трассировка не может доказать, что они не понадобятся. Убрать — значит компилировать MDX в отдельный артефакт заранее, и это записано в границы v1, а не выдано за уже сделанное.

Три стадии — `deps`, `builder`, `runner` — нужны ради кэша: в `deps` копируются
только манифесты, поэтому слой с `npm ci` переиспользуется на каждой сборке, где
зависимости не менялись. Скопировать исходники туда же — значит инвалидировать
установку на каждой правке.

Валидация контента запускается **и внутри сборки образа**. Образ — это то, что
уезжает в прод, поэтому не должно быть способа собрать его из контента, который CI
бы отверг.

## Решение 6: `mediaUrl()` из трёх строк

```ts title="src/content/media.ts"
const BASE = process.env.MEDIA_BASE_URL ?? '/media'

export function mediaUrl(path: string): string {
  return `${BASE.replace(/\/+$/, '')}/${path.replace(/^\/+/, '')}`
}
```

Эти три строки не нужны сегодня. Медиа лежит в `public/media`, и всё работает.

Они нужны потому, что git — плохой дом для видео, и переезд на объектное
хранилище неизбежен. С этой функцией переезд — одна правка и одна переменная
окружения. Без неё каждый `<Figure>` в каждой статье держит зашитый путь, и
миграция превращается в поиск-замену по контенту, чьи ошибки видны только как
битые картинки в проде.

Это конкретная форма принципа «заложить, но не делать»: `locale` и `status` в
схеме — из той же категории.

## Чего здесь сознательно нет

Каждый пункт назван с условием, при котором его стоит добавить.[^granica]

| Не делаем                   | Когда добавляется                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------- |
| ISR и on-demand revalidate  | когда время сборки перестанет устраивать — порядка нескольких тысяч документов     |
| Внешнее объектное хранилище | когда медиа перестанет комфортно жить в репозитории; переезд — замена `mediaUrl()` |
| HLS и транскодирование      | когда появятся длинные видео или заметный трафик                                   |
| Поиск                       | Pagefind ставится за час поверх собранного вывода, закладывать нечего              |
| Роутинг по локалям          | `locale` в схеме уже есть; роутинг — когда появится второй язык                    |
| Расписание публикаций       | `status` уже есть; расписание требует рантайма                                     |
| Редакторский UI             | не планируется; frontmatter держим плоским, чтобы Decap подключался без миграции   |
| Аналитика и мониторинг      | в v1 хватает логов Caddy                                                           |
| Формы и комментарии         | требуют рантайма, выносятся отдельным решением                                     |

Отсутствие с объяснением — это решение. Отсутствие без объяснения — недоделка. Эта
таблица существует, чтобы разница была видна.

## Что это стоит

Честно про минусы, потому что их наличие — тоже часть выбора:

- **Публикация требует сборки и деплоя.** Опечатку не поправить из браузера за
  минуту. Для сайта, который правят по десять раз в день, это неподходящая
  архитектура.
- **Двести строк загрузчика**, которых не было бы при контенте в `app/`.
- **Нет редакторского интерфейса.** Автор пишет MDX и делает PR. Для нетехнической
  редакции это блокер, и его решает Decap или Sveltia — но это отдельное решение.

Окупается там, где контент живёт дольше текущей структуры каталогов и где важно,
чтобы сайт не разъезжался с тем, что о нём написано в README.

[^yaml]:
    Строго говоря, `gray-matter` использует `js-yaml`, и это поведение
    соответствует спецификации YAML 1.1, а не ошибка библиотеки. Именно поэтому
    правильное решение — принять оба варианта, а не «починить» парсер.

[^granica]:
    Формулировка условия важнее самого списка. «Пока не нужно» через полгода
    читается как «забыли»; «когда документов станет несколько тысяч» остаётся
    проверяемым утверждением.
